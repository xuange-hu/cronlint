## Pass 1: expression

### `CRN001` — Schedule does not parse

**Severity** high (score 4)

A schedule cron cannot parse is not a schedule: depending on the implementation the line is rejected outright or silently dropped, so the job never runs and nothing says so.

**Fix.** Fix the field count and the values, then confirm with `crontab -l` or `run-parts --test`.

### `CRN002` — Six-field schedule (leading seconds)

**Severity** high (score 4)

Standard cron and cronie take five fields. With six, the fifth is read as the start of the command and the sixth as its first argument: the job still installs, runs something unintended at the wrong time, or fails on every tick.

**Fix.** Drop the seconds field, or run it on a scheduler that documents six fields (quartz, systemd timer).

### `CRN003` — Seven-field schedule (trailing year)

**Severity** medium (score 3)

A trailing year is a quartz convention. cronie and vixie read only the first five fields and treat the rest as the command, so a job written to run in one year runs every minute of every year instead.

**Fix.** Remove the year field and gate it in the command, or move the job to a scheduler that accepts it.

### `CRN004` — Unknown @special

**Severity** high (score 4)

`@every 5m` and friends belong to other schedulers. cron leaves the line unrunnable, so the task is installed and never fires.

**Fix.** Use a standard special (@reboot, @hourly, @daily, @weekly, @monthly, @yearly) or write the fields out.

### `CRN005` — Schedule with no command

**Severity** high (score 4)

A schedule whose command column is empty is either a truncated line or a typo; cron accepts it and does nothing, which reads as a job that 'used to work'.

**Fix.** Restore the command, or delete the line.

### `CRN006` — Day-of-month and day-of-week are both restricted

**Severity** low (score 1)

When both fields are restricted cron ORs them, it does not AND them: '0 0 1 * mon' fires on the 1st AND on every Monday, which surprises everyone who wrote it expecting the intersection.

**Fix.** Restrict one field to * if you meant the intersection, and check the run log for the days you did not expect.

### `CRN007` — Weekday written as 7

**Severity** note (score 1)

0 and 7 both mean Sunday in vixie cron, but not every implementation accepts 7. A file that works on one host and is rejected on the next is a portability trap.

**Fix.** Write 0 for Sunday.

### `CRN008` — Field value out of range

**Severity** high (score 4)

Minute 60, hour 24 or month 13 make the whole line unparsable on most crons. Where a lenient parser accepts it the job simply never matches any date.

**Fix.** Bring every value inside its field's range.

### `CRN009` — Step or range is malformed

**Severity** high (score 4)

`*/0` divides by zero in the reader, `10-5` never matches, and an unknown name like `xyz` is not a weekday. Each one takes the whole line down with it.

**Fix.** Use a positive step, a low-to-high range, and a real month/weekday abbreviation.

## Pass 2: task

### `CRN010` — Command is not an absolute path

**Severity** high (score 3)

cron runs with a minimal PATH (usually /usr/bin:/bin). A bare name resolves against whatever the cron daemon inherited, which is often empty -- the job fails silently -- or, on a box where someone edited root's crontab PATH, resolves to a different program entirely.

**Fix.** Write the full path: /usr/local/bin/job, not job.

### `CRN011` — World-writable directory in the command

**Severity** high (score 4)

/tmp and /var/tmp are sticky but still attacker-writable: a symlink placed between the schedule and the run redirects the write, and a program dropped there first is the one that executes.

**Fix.** Keep the program and its data under a directory only root can write.

### `CRN012` — Unquoted variable expansion

**Severity** medium (score 2)

cron expands nothing itself, but the shell the command runs under does. An unquoted $NAME containing spaces or glob characters is split into words and pathname-expanded before the program sees it, which is how a backup path becomes two arguments and a wildcard becomes every file in the directory.

**Fix.** Quote it: "$NAME", and quote the path it expands into.

### `CRN013` — Command substitution in a scheduled command

**Severity** medium (score 2)

Whatever the substitution returns becomes words in the command line. If it reads a file an unprivileged process can write, that content is executed as arguments at the next tick.

**Fix.** Resolve the value once, outside the schedule, and pass it in explicitly.

### `CRN014` — Credential on the command line

**Severity** critical (score 6)

cron's children inherit the terminal-less environment, but the argument vector is world-readable in /proc while the job runs: any local user can `ps` it, and it lands in shell history files and in any process accounting the box keeps.

**Fix.** Read the secret from a root-only file or a keyring; never put it in the command.

### `CRN015` — Download piped into a shell

**Severity** critical (score 6)

The script that runs is whatever the server returns at that moment. Scheduled, unattended and usually root: it is the most reliable way to turn someone else's outage into your compromise.

**Fix.** Fetch to a file, verify a signature or a pinned hash, then execute the verified copy.

### `CRN016` — Redirect onto a block device

**Severity** critical (score 6)

Writing to /dev/sda destroys the partition table rather than a file. A typo in a path here is unrecoverable and runs unattended.

**Fix.** Redirect to a log file under /var/log, never to a device node.

### `CRN017` — Overwrite redirect onto a system path

**Severity** high (score 4)

`> /etc/passwd` truncates before the command runs: even a failing job has already emptied the file. Append (`>>`) does not have this failure mode.

**Fix.** Use >> for logs, and write generated config to a temp file you rename.

### `CRN018` — Recursive delete with a variable or a broad root

**Severity** high (score 4)

`rm -rf $TARGET` with an unset TARGET becomes `rm -rf /`'s argument list with an empty word dropped -- but with a set-but-wrong one it is the whole tree, unattended, as root.

**Fix.** Guard it: refuse to run when the variable is empty, and delete a fixed, narrow path.

### `CRN019` — Job runs with no log destination

**Severity** low (score 1)

cron mails stdout to the user when there is an address and discards it otherwise. A job that fails at 03:00 with no redirect leaves no trace, which is how a broken backup stays broken for a year.

**Fix.** Append to a log: `>> /var/log/job.log 2>&1`, or pipe to logger.

### `CRN020` — Command needs an interactive terminal

**Severity** medium (score 2)

cron has no tty and no DISPLAY. Anything that needs one fails on the first tick, usually with an error that only appears if you were watching.

**Fix.** Use the non-interactive form of the tool, or move the job to a session that has a display.

### `CRN021` — Script without a shebang

**Severity** low (score 1)

Without `#!` the kernel falls back to the shell that execs it, which is /bin/sh under cron even when the file uses bash-only syntax. The same script works from your terminal and fails at 03:00.

**Fix.** Put a shebang on line 1 and make it executable.

### `CRN022` — Task runs as root

**Severity** medium (score 2)

Every bug in the command is then a root bug. Most scheduled jobs need one directory's worth of access, not the whole box.

**Fix.** Name a dedicated user in the user column, and give that user only what the job touches.

### `CRN023` — Every minute

**Severity** medium (score 2)

Once a minute is the densest schedule cron offers. Any job longer than 60 seconds then runs into itself, and the failure mode is two copies of a backup writing over each other.

**Fix.** Widen the interval, or make the job take a lock so a second copy exits immediately.

### `CRN024` — Environment line is not quoted

**Severity** low (score 1)

cron splits environment lines on whitespace after the `=`. A value with spaces is truncated at the first one, so PATH or BACKUP_DIR is silently shorter than it looks.

**Fix.** Quote the value: DIR="/var/backups".

### `CRN025` — PATH points at a world-writable directory

**Severity** high (score 4)

cron resolves every bare command against this PATH. With /tmp in it, any local user who drops /tmp/ls first wins the race for every scheduled job on the box.

**Fix.** Keep PATH to system directories: /usr/local/bin:/usr/bin:/bin.

### `CRN026` — Two timezone settings in one file

**Severity** medium (score 2)

TZ and CRON_TZ are honoured by different implementations. Setting both, or setting one and relying on the other, means the file means different hours on different hosts.

**Fix.** Set exactly one of them, and say which in a comment.

## Pass 3: file

### `CRN050` — Duplicate schedule

**Severity** medium (score 2)

The same schedule twice means the command runs twice at the same instant. That is two writers on one output file, or a job that takes twice as long as it looks.

**Fix.** Delete the duplicate, or give it a different time if you meant two runs.

### `CRN051` — Same script scheduled more than once

**Severity** medium (score 2)

Two schedules for one program is either a leftover or an overlap: if one run has not finished when the next starts, they contend for the same files and the last one wins.

**Fix.** Keep one schedule, or make the program lock so a second instance exits.

### `CRN052` — Two tasks fire in the same minute

**Severity** medium (score 2)

Tasks that share a minute share a machine: two backups, a backup and a rotation, anything with a lock file. On a small box the second one waits, times out, or collides with the first.

**Fix.** Stagger the minutes, or make both jobs lock-aware.

### `CRN053` — Two tasks write the same log file

**Severity** low (score 1)

Two appends into one file interleave line by line. The log still looks fine and is useless for telling which job said what.

**Fix.** One log per job, or a logger that tags each line with its source.

### `CRN054` — Every-minute job with no lock

**Severity** high (score 3)

A job that fires every minute and has no lock, no `flock -n` and no pidfile check will overlap itself as soon as it takes longer than a minute -- and the overlap is silent.

**Fix.** Wrap it: `flock -n /run/job.lock /path/to/job`.

### `CRN055` — Many tasks share one minute

**Severity** low (score 1)

Everything scheduled at the same minute starts at once. On a small host that is a load spike, and any job with a timeout loses.

**Fix.** Spread them across minutes; cron has 60 of them.

### `CRN056` — File has no scheduled tasks

**Severity** note (score 1)

A crontab with only comments and environment lines schedules nothing. If that was not intended, the jobs are missing; if it was, the file is dead weight.

**Fix.** Add the schedules, or delete the file so it stops looking like a source of jobs.

### `CRN057` — Schedule line is very long

**Severity** low (score 1)

Implementations cap a line at a few hundred to a few thousand characters. Past the cap the command is cut mid-word, and the job runs something that is not what you wrote.

**Fix.** Move the logic into a script and schedule that.

### `CRN058` — Task reads a file another task writes in the same minute

**Severity** medium (score 2)

Two tasks that share a minute and touch the same path have an undefined order: the reader can see a half-written file, and which one wins depends on the scheduler, not on you.

**Fix.** Give the writer an earlier minute, or have the reader wait for a sentinel.
